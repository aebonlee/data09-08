# Supabase DB 스크립트 — data09-08 초도품 치수검사 · 협력사 일일점검

이 폴더에는 초도품 치수검사 판정(과제 A)과 협력사 일일점검 현황(과제 B) 도구의 자료를 데이터베이스(Supabase)에 담을 때 쓸 표 구조(`schema.sql`)가 들어 있습니다.
지금 도구는 이 스크립트 없이도 그대로 동작합니다. 앱을 DB 에 연결하는 일은 다음 단계에서 합니다.

## 왜 DB 가 필요한가

지금 도구는 검사 건·기준표·측정결과·점검 데이터를 브라우저 localStorage 의 `data09-08.db` 한 덩어리에, 도면 이미지를 `data09-08.img.<검사건>` 에 둡니다. 그래서 다음 한계가 있습니다.

- **용량** — 도면 이미지는 한 장에 수 MB 입니다. 브라우저 저장 공간(보통 5MB 안팎)은 도면 몇 장이면 찹니다. 그러면 도구가 메모리에만 두고, 새로 고치면 사라집니다.
- **이력 추적** — 기획서가 말하는 「원본 도면·측정파일과 최종 판정의 연결·추적」, 품번·Rev·업체·LOT별 조회는 검사 건이 한곳에 쌓여야 가능합니다.
- **협력사·본사 공유** — 과제 B 는 여러 협력사가 올린 점검 데이터를 본사가 모아 보는 구조입니다. 브라우저에만 있으면 모을 수 없습니다.

## 테이블

| 이름 | 용도 | localStorage 대응 |
|---|---|---|
| `app_settings` | 판정 설정(항목명 매칭, 판정 전 반올림, 빈 단위 처리), 같은 값 반복 검사 기준, 마지막으로 연 검사 건. 사용자당 1행 | `db.settings`, `db.daily.repeat_days`, `db.current` |
| `import_template` | 열 지정 템플릿 — 장비·양식별 「어느 열이 측정번호·측정값인지」 | `db.templates[]` |
| `inspection` | 검사 건 — 품번, Rev, LOT, 검사일, 업체, 검사자, 도면 파일 이름 | `db.inspections[]` |
| `dim_spec` | 치수 기준표 — 항목번호, 항목명, 치수 종류, 기준값, 상·하한 공차, 단위, 소수점 자리수 | `inspections[].spec[]` |
| `measurement` | 측정결과 — 측정번호, 항목명, 측정값, 단위, 출처(CMM·수기) | `inspections[].meas[]` |
| `drawing_pin` | 도면 위 항목 핀의 비율 좌표(0~1) | `inspections[].pins{}` |
| `equipment` | 협력사 설비 목록 — 협력사, 설비, 촬영 순서 | `db.daily.equipment[]` |
| `daily_check` | 일일점검 데이터 — 협력사, 점검일, 설비, 점검항목, 판정, 측정값, 원본 사진 | `db.daily.records[]` |
| `check_limit` | 점검항목별 관리 기준값(하한·상한) | `db.daily.limits[]` |
| `check_sheet` | 월간 점검표 격자(2026-09-29) — 양식·협력사·설비·연월·사진 찍은 날·휴무일·설비별 관리 범위, 칸 값은 `cells` jsonb(`항목|날짜|교대` → ✓·×·숫자, 서명은 이름 대신 ✓) | `db.daily.grids[]` |

필드 이름은 도구의 이름을 그대로 씁니다. 몇 가지는 달리 두었습니다.

- 기준값·공차·측정값·점검 측정값은 **입력된 글자 그대로**(text) 둡니다. 도구는 숫자로 읽지 못한 값을 버리지 않고 「확인필요」로 드러내는 것이 설계 의도라, 숫자 칸으로 두면 그런 행을 DB 가 받지 못합니다.
- 기준표의 같은 항목번호 중복도 도구가 「확인필요」로 드러내므로 막지 않습니다. 대신 화면 순서(`line_no`)를 검사 건 안에서 한 번만 쓰게 했습니다.
- 도면 이미지는 표에 넣지 않습니다. 앱 연결 단계에서 Supabase Storage(비공개 버킷)에 올리고 `inspection.drawing_image_path` 에 경로만 적습니다.
- 설비의 순서 칸 `order` 는 PostgreSQL 예약어라 쿼리에서 `"order"` 처럼 따옴표로 씁니다.

## 보안

- 모든 표에 RLS(행 단위 보안)를 켰습니다. 각 행은 만든 사람(`owner_id`)만 보고 고치고 지울 수 있습니다.
- 기준표·측정결과·핀은 본인 검사 건에만 붙일 수 있습니다.
- 로그인하지 않은 방문자(anon)는 아무것도 보거나 쓰지 못합니다. 과제 B 의 협력사 업로드 링크를 만들 때도 로그인을 거치게 하거나, 업로드 전용 함수를 따로 설계해야 합니다.
- 지금 도구에는 로그인·역할(본사·협력사) 구분이 없어 관리자 표를 두지 않았습니다. 협력사별 접근을 나누는 일은 앱 연결 단계에서 정합니다.

## 적용 방법

1. [supabase.com](https://supabase.com) 에 가입합니다.
2. **New project** 로 본인 프로젝트를 만듭니다.
3. 왼쪽 메뉴의 **SQL Editor** 를 엽니다.
4. `schema.sql` 내용을 모두 복사해 붙여 넣습니다.
5. **Run** 을 누릅니다.

여러 번 실행해도 안전합니다. 이미 있는 표는 건너뛰고, 정책과 트리거는 지우고 다시 만듭니다.

## 확인 방법

- **Table Editor** 에 표 9개가 보이면 됩니다.
- 표마다 **RLS enabled** 표시가 있는지 확인합니다.
- SQL Editor 에서 아래를 실행해 정책이 표마다 4개(조회·추가·수정·삭제)인지 봅니다.

```sql
select tablename, count(*) from pg_policies where schemaname = 'public' group by tablename;
```

## 앱 연결은 다음 단계입니다

이 스크립트는 표를 준비해 두는 것까지입니다. 도구의 `js/store.js` 를 Supabase 에 읽고 쓰도록 바꾸는 일, 로그인 화면과 도면 이미지 업로드(Storage)를 붙이는 일은 다음 단계에서 합니다.
그때 저장은 upsert 로 하고, 충돌 기준을 표마다 지정해야 중복 행이 생기지 않습니다.

- 템플릿 `owner_id,kind,name` · 검사 건 `owner_id,insp_key` · 핀 `inspection_id,no`
- 설비 `owner_id,vendor,equip` · 점검 데이터 `owner_id,vendor,date,equip,item` · 기준값 `owner_id,item`

점검 데이터의 「덧붙이기」는 upsert 로 바꿔야 합니다. 지금 도구는 같은 줄을 두 번 덧붙일 수 있지만 DB 는 협력사·점검일·설비·항목이 같은 줄을 한 번만 받습니다.

## 로컬 검증 방법

운영에 올리기 전에 내 PC 의 임시 PostgreSQL 에 실제로 적용해 검사합니다. PostgreSQL 이 설치되어 있어야 합니다(macOS: `brew install postgresql@17`).

```sh
./scripts/sqltest/run.sh
```

임시 데이터베이스를 만들어 `schema.sql` 을 두 번 적용하고, 사용자 A·B 격리, 비로그인 차단, 제약 조건, 함수 권한을 검사한 뒤 지웁니다. 마지막에 「SQL 검증 통과.」가 나오면 됩니다.
`scripts/sqltest/` 의 `*.local.sql` 파일은 검증 전용이라 Supabase SQL Editor 에서 실행하면 스스로 멈춥니다.
